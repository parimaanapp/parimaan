## 2. Common Issues

_To be filled in as encountered — do not wait for W22._

Anticipated from `SYSTEM_DESIGN.md` §14 failure modes:

### Sprint 0 issues encountered (real, logged as they happened)

- **`pnpm@latest` via corepack requires Node ≥22.13**, incompatible with the locked Node 20 Lambda runtime decision. Fixed by pinning `pnpm@9.15.9` explicitly (`packageManager` field in root `package.json`) rather than using `latest`. Local dev Node version and Lambda deployment target don't have to match exactly, but the package manager does need to support whichever Node version is actually active locally.
- **`nvm use` piped through another command (`nvm use 20 | tail -1`) does not persist** — pipes run in a subshell, so PATH changes don't propagate back to the parent shell. Always run `nvm use` unpiped, chained with `&&` to subsequent commands in the same invocation.
- **`verbatimModuleSyntax: true` (inherited from the shared base tsconfig) conflicts with `module: CommonJS`** in `infra/tsconfig.json` — CDK's CommonJS convention doesn't support the strict ESM-syntax-preservation that flag requires. Fixed by overriding `verbatimModuleSyntax: false` for the `infra` package specifically.
- **`exactOptionalPropertyTypes: true` correctly rejected** `{ account: process.env.X }` where `process.env.X` is `string | undefined` — an optional property must be *absent*, not present-with-value-undefined. Fixed with conditional object spread: `...(x ? { account: x } : {})`.

### W1 issues encountered

- **CDK `Vpc` (concrete class) assigned to a parameter typed `IVpc` fails under `exactOptionalPropertyTypes`** — a structural mismatch in aws-cdk-lib's own type declarations (`IVpc.vpnGatewayId` declared `?: string`, `VpcBase`'s implementation is a getter returning `string | undefined`), not a real bug. Confirmed empirically (removed the cast, saw the exact error; confirmed `vpnGatewayId` isn't consumed by any construct that needed it). Fixed with a single narrow, documented `as IVpc` cast at the point of use — not a project-wide flag change.
- **CloudFormation's `AWS::EC2::SecurityGroup` `GroupDescription` has an unusually restrictive allowed-character pattern** — an em-dash (`—`) in a description string produces a real CFN validation warning (would likely fail at actual deploy time, not just a synth-time cosmetic issue). Other resource-facing strings (e.g. CDK `Stack`-level `description` props, which map to the template's top-level `Description` field) don't have this restriction — confirmed by checking whether the same warning recurred elsewhere after the fix. Fixed by using a plain hyphen instead. Worth a quick grep for em-dashes in any new resource-facing string property (not code comments) before adding one.
- **Vitest's default 5000ms `testTimeout` is too tight for `cdk synth`'s cold-start cost on GitHub Actions' shared runners** — passed comfortably on a local warm-cache Mac, then failed in CI on PR #5 with every stack's first `synthesizes without error` test timing out at exactly 5000ms. The cost is aws-cdk-lib + jsii module load/runtime init, paid once per Vitest worker (later synth calls in the same worker are fast). Fixed with `infra/vitest.config.ts` setting `testTimeout: 15_000`. **Lesson: always watch CI run to completion for a new stack's first PR, don't assume local-green implies CI-green** — this one was invisible locally no matter how many times the suite was re-run.
- **`pnpm exec esbuild` (invoked internally by CDK's `NodejsFunction` bundling) couldn't resolve the `esbuild` binary** when `esbuild` was only installed as a devDependency in `infra/`. Root cause, verified: `aws-cdk-lib`'s bundling code detects `esbuild` via a plain `require('esbuild/package.json')` from deep inside its own module tree, which walks Node's CommonJS resolution up through the true top-level `node_modules/` — an `infra/`-scoped, non-hoisted install is never on that path under pnpm's strict per-package linking. Fixed by adding `esbuild` as a **root** devDependency, matching the existing pattern (shared toolchain deps — `typescript`, `eslint`, `vitest` — already live at the root, not per-package).
- **`nodejs20.x` Lambda runtime is already deprecated** (CFN validation warning, confirmed on every `ApiStack` synth): deprecated 2026-04-30, new-resource creation disabled 2027-02-01, updates disabled 2027-03-03. Node 20 was a locked architectural decision (`SYSTEM_DESIGN.md` §18) — surfaced to the user directly rather than silently changed. **Resolved**: bumped to `Runtime.NODEJS_24_X` (AWS's own suggested target in the warning) while only one Lambda existed, keeping the blast radius to one file. **Deliberately decoupled from local dev tooling** — `.nvmrc`/pnpm/CI stay on Node 20; only the deployed Lambda runtime moved. Confirmed via re-synth: the deprecation warning is gone, esbuild's bundling target auto-derives from the `runtime` prop with no separate config needed.
- **`@testcontainers/postgresql@12.x` (latest) requires Node ≥22.22** (declared in `testcontainers`'s own `engines` field) — installing it on our locked Node 20 local-dev tooling produced a runtime error deep in an internal HTTP wait-strategy (`webidl.util.markAsUncloneable is not a function`, from a Node-version-mismatched bundled `undici`), not a clean "wrong Node version" message. Verified the actual root cause via `npm view testcontainers engines` before touching anything, rather than guessing at the cryptic error. **Resolved**: pinned `@testcontainers/postgresql` to `^11.14.0` (the last v11.x, which declares no `engines` constraint and was confirmed empirically — not assumed — to run cleanly on Node 20.20.2, including full container boot and query execution). This is real, ongoing tooling debt: v11.x isn't actively developed anymore, and staying on Node 20 for local dev/CI will keep forcing pins like this on any tool that raises its own Node floor. Worth revisiting if the Lambda-runtime/local-dev decoupling (see the entry above) gets reconsidered.
- **A table's RLS `CREATE POLICY` referencing another table in its `USING` subquery creates a real drop-order dependency, not just an FK-style one.** `household_settings`'s policy subquery reads from `household_memberships`, and Postgres records that as a dependency of the policy on `household_memberships` — so `DROP TABLE household_memberships` (even with no CASCADE, even though nothing FK-references `household_memberships` from `household_settings`) fails with "cannot drop table household_memberships because other objects depend on it" if `household_settings` (and its policy) haven't been dropped first. Caught via the baseline-schema migration's `up`-then-`down` reversibility test. First instinct was to add `CASCADE` to the `DROP TABLE` statements, but a database-reviewer agent correctly flagged that as masking, not fixing, the issue — `CASCADE` would silently vaporize the dependent policy instead of surfacing an ordering bug, and would keep doing so even if a *future* migration's `down()` forgot to drop something real. **Resolved**: reordered `down()` to drop `household_settings` before `household_memberships`, with no `CASCADE`. Lesson: a table's `down()` drop order must account for anything that reads it in an RLS policy's `USING`/`WITH CHECK` clause, not just literal `REFERENCES` foreign keys.
- **node-pg-migrate's error-path SQL logging leaks secrets embedded in migration DDL — unconditionally, not just under `verbose`.** The `parimaan_app` role migration embeds its password directly in `CREATE ROLE ... PASSWORD '<secret>'` SQL text (Postgres DDL has no bind-parameter mechanism to avoid this). A security review of that migration found that while node-pg-migrate's default (non-verbose) logger omits routine SQL text, its query-error path (`db.js`'s `query()` catch block) logs the **full failing statement**, including the literal password, on any query failure — role-already-exists, a transient connection error, anything — regardless of the `verbose` setting. **Resolved**: `runMigrations()` now accepts an optional `secretsToRedact: readonly string[]` array, wired into a custom `logger` (see `api/src/db/redactingLogger.ts`) passed to `runner()`, which substitutes any known secret value out of every log line before it reaches `console`. The migration-runner Lambda passes both the Aurora admin password and the app-role password into this array on every invocation. Lesson: a library's own error/debug logging can be a secret-leak path independent of anything the calling code does right — worth checking explicitly whenever a secret has to be embedded in a raw string (SQL, shell command, etc.) that a third-party tool might echo back on failure.
- **CDK's `NodejsFunction` bundling defaults to CJS output (`OutputFormat.CJS`), which silently breaks any bundled module using `import.meta.url`.** `api/src/db/runMigrations.ts` computes its default migrations directory via `dirname(fileURLToPath(import.meta.url))` — under esbuild's CJS output, `import.meta` becomes empty (a build-time warning, easy to miss: "`import.meta` is not available with the `cjs` output format and will be empty"), so `fileURLToPath(undefined)` would throw at Lambda cold start the moment the module is imported, before the `MIGRATIONS_DIR` env-var override even gets a chance to matter — this would have crashed the migration-runner Lambda immediately on first real invocation despite `cdk synth` succeeding and every unit test passing (synth never executes the bundled code, only compiles it). Caught by reading the esbuild warning in a CDK synth's own console output during test runs, not by any test itself. **Resolved**: explicitly set `bundling.format: OutputFormat.ESM` on the migration-runner `NodejsFunction` (Node 24's Lambda runtime supports ESM natively). Lesson: an esbuild bundling warning printed during `cdk synth`/tests is not just noise — read it, especially for any Lambda whose source uses `import.meta`.
- **CDK's `SecurityGroup.addIngressRule()` does not add the rule inline to the target security group's own `SecurityGroupIngress` property when the peer is another `SecurityGroup` construct — it creates a separate `AWS::EC2::SecurityGroupIngress` resource instead.** A test asserting on the DB security group's own `Properties.SecurityGroupIngress` array (matching the pattern used elsewhere in this codebase for CIDR-based rules) failed with an empty array even though the rule was genuinely present in the synthesized template, just as a sibling resource referencing the SG by `GroupId`/`SourceSecurityGroupId`. Confirmed via a throwaway debug test dumping `template.findResources('AWS::EC2::SecurityGroupIngress')`. Lesson: don't assume CDK's synthesized shape for a given L2 method call without checking — SG-to-SG rules and SG-to-CIDR rules take genuinely different template shapes.
- **`NodejsFunction`'s `bundling.nodeModules` shells out to a fresh package-manager install *inside an ephemeral bundling temp directory* — this passed reliably in local dev and failed on every run in CI, with only a bare `pnpm install ... exited with status 1` and no further detail.** Used to keep `node-pg-migrate` un-bundled (esbuild can't statically bundle its runtime `jiti`-based `.ts` file loading). Locally green every time (PR #9's own local test runs all passed); GitHub Actions CI failed the same way on every retry, `Failed to bundle asset ... CommandExitedWithNonZeroStatus`. Root cause not fully isolated (candidates: corepack's `packageManager`-pin resolution not applying to a CWD outside the repo tree, network-egress differences on the runner, or a pnpm-version mismatch between what CI's shell has on `PATH` vs. what corepack activates) — rather than chase an intermittent, environment-dependent failure in a mechanism that needs network access at every `cdk synth`/test run regardless of cause, replaced the mechanism entirely. **Resolved**: `node-pg-migrate` is now `externalModules` (left as a bare `import`, never bundled) and copied directly from this repo's own already-installed `node_modules` via `cp -RL` in `afterBundling`, resolved at synth time via `require.resolve('node-pg-migrate/package.json', { paths: [apiPackageDir] })`. `-RL` dereferences pnpm's symlinked `.pnpm` store layout recursively, so the copy includes node-pg-migrate's own nested dependencies (`jiti`, etc.) as real files, not symlinks — a fully self-contained copy with zero network calls or package-manager invocations at bundle time, using only what the one `pnpm install --frozen-lockfile` step (already run by both CI and local dev) already put on disk. Confirmed empirically: local `cdk synth`/test time for this stack dropped from ~130s to ~19s with this change, consistent with removing a network round-trip from every single synth call. Lesson: prefer copying already-installed dependencies over having CDK's bundling shell out to install fresh ones — it's faster, deterministic, and removes an entire class of CI-only network/environment flakiness.
- **A test's `/\d{12}/` "no embedded AWS account id" regex is a real false-positive risk once a stack bundles a Lambda.** `data-stack.test.ts`'s account-id guard failed after the `nodeModules`→manual-copy bundling change above, because the new bundle produced a different content-hash S3 asset key, and that 64-character hex hash happened to contain 12 consecutive digits (`...1125772837209...`) by pure chance — nothing to do with a real account id. The same broad regex existed in `network-stack.test.ts`, `auth-stack.test.ts`, and `api-stack.test.ts` too, all of which carry the same latent risk (api-stack bundles the `health` Lambda). **Resolved**: tightened all four to `/"\d{12}"/` — a real embedded account id appears as its own quoted JSON string value, not as a substring of a much longer hex hash, so bounding the digits with quotes catches the real case without the false-positive risk. Lesson: any regex-based "no secret/id leaked" assertion against a full synthesized-template JSON dump needs to account for legitimately long random-looking strings (content hashes, asset keys) already present in the template — a broad numeric-run pattern will eventually collide with one by chance.
- **A Zod env-schema required a variable (`DB_SECRET_ARN`) that the CDK stack deliberately never sets on the Lambdas that schema validates for — every cold start of `me`/`createHousehold`/`userHouseholds` would have thrown a `ZodError` in real AWS, and none of 166 passing tests caught it.** `api/src/db/config.ts`'s `loadDbConfig()` required `DB_SECRET_ARN` (the Aurora *admin*-credentials secret ARN), but `infra/stacks/api-stack.ts`'s `createDbResolverFunction` only ever sets `APP_ROLE_SECRET_ARN`/`DB_HOST`/`DB_PORT`/`DB_NAME` on these three resolver Lambdas — by design, since they must connect as the least-privileged `parimaan_app` role only, never the cluster admin. `DB_SECRET_ARN` was also, separately, dead code: `db/pool.ts` never read `config.dbSecretArn` anywhere. The gap was invisible to every test because every resolver test injects `getPool`/`config` directly, bypassing `loadDbConfig()`'s real env-parsing entirely — a typescript-reviewer agent caught it by tracing the actual data flow from `config.ts`'s schema through to what `infra/stacks/api-stack.ts` actually sets, not by running anything. **Resolved**: removed `DB_SECRET_ARN` from `envSchema`/`DbConfig` entirely, since it was both unset-in-production and unused-in-code. Lesson: a required env var in application code and what the deploying CDK stack actually sets are two independent sources of truth that can silently drift — worth an explicit cross-check (or a shared constant/type) between a Lambda's env-schema and its CDK `environment` block, especially since per-Lambda dependency-injected tests can mask exactly this class of gap.
- **A per-account rate limiter on `joinHousehold` is a real, correctly-implemented mitigation against a single scripted guesser, but does not close the invite-code guessing-attack gap `api/src/domain/inviteCode.ts` originally flagged as a must-fix-before-ship item.** `api/src/rateLimit/joinAttemptLimiter.ts` caps join attempts at 20/day, keyed by the caller's `userId`, enforced via a single atomic DynamoDB `UpdateItem` with a `ConditionExpression` (race-safe against concurrent Lambda invocations — confirmed no read-then-write gap). A security review pointed out this only throttles *one authenticated Cognito identity*: nothing in this system rate-limits Cognito account creation itself, so an attacker willing to script account creation gets `N × 20` guesses/day fully parallelized across `N` accounts, with no cross-account correlation performed anywhere. Against an 887M-code keyspace, this multiplies the attacker's cost by roughly a constant (the cost of one more account), not by anything that scales with the keyspace — for a single account it's real; for a Sybil attacker it's closer to friction than a fix. **Not resolved in this PR** — tracked as a follow-up task (IP-based limiting and/or friction on account creation) rather than silently treating the per-account limiter as having fully closed the original gap. Lesson: a rate limiter's real effectiveness depends on what identity it's keyed to being expensive for an attacker to acquire more of — a limiter keyed to a cheaply-mintable identity (a fresh Cognito account via self-service SSO) bounds a *single* attacker's rate, not the population of attackers.

### W4 household-lifecycle slice (`rotateInviteCode` / `leaveHousehold` / `deleteHousehold`) — accepted gaps, recorded not silently carried

- **`households` still has no RLS policy, and two new mutations now write to it.** `rotateInviteCode`'s `updateInviteCode` (an `UPDATE ... WHERE id = $1`) and `deleteHousehold`'s `DELETE ... WHERE id = $1` are protected entirely by the resolver-level `requireHouseholdMember` gate (SD §6.2 layer 2) plus the statement's own `WHERE id = $1` scoping. There is no layer-3 backstop: `householdRepository.test.ts` contains a deliberate test (`NO-RLS-BACKSTOP`) proving that calling `updateInviteCode` directly, as a non-member, *succeeds* — the mirror image of the RLS-only regression test that proves `updateSettingsPartial` is blocked. **Same accepted-gap category as task #28** (`households` RLS deferred). Enabling RLS on `households` is not a drop-in fix: any member-only policy would break `joinHousehold`'s `SELECT ... FOR UPDATE` lookup by invite code, which by definition runs for a caller who is *not yet* a member — so the policy would need a second, invite-code-shaped predicate designed alongside it. Blocking prerequisite for anyone picking that up: re-run `joinHousehold.test.ts`'s cap-under-concurrency test, which depends on that row lock working.
- **`household_memberships` now has its first `DELETE` (via `leaveHousehold`), and that table has no RLS policy either.** `deleteNonPrimaryMembership`'s three `WHERE` predicates are the only protection that exists: `household_id` scopes it, `user_id` is the sole thing preventing a member from evicting a co-member, and `role <> 'primary'` is the sole thing preventing a household from becoming primary-less (nothing downstream is built to handle that state). Dropping any one predicate is a privilege-escalation or data-integrity bug that no other layer will catch — there is no third layer. A repository test asserts the `user_id` predicate empirically (a mismatched user id deletes zero rows) rather than trusting the doc comment. Treat any future edit to that statement as a security change, not a query tweak.
- **A rotated-away invite code returns to the free keyspace and could, in principle, be reissued to a different household later.** Rotation does not blacklist the old code; `households_invite_code_key` only enforces uniqueness among codes currently in use. So a code a user still has written down could — at roughly 1-in-887M per subsequently minted code — later become a valid code for someone else's household. Accepted, not overlooked: a blacklist table would grow unbounded, would need its own expiry policy, and would shrink the effective keyspace over time. Recorded here so it is a known accepted risk rather than a silent gap. Would need revisiting only if invite-code lifetime semantics change (e.g. permanent per-household codes, or codes printed on physical material).
- **`notification_preferences` (a future table) will NOT be cleaned up by either `leaveHousehold` or `deleteHousehold` as they stand.** `deleteHousehold` relies entirely on `ON DELETE CASCADE` from `households` — verified against `migrations/1787072268736_baseline-schema.ts`, where both `household_memberships` and `household_settings` declare it (referential-integrity actions bypass RLS, so the cascade reaches RLS-protected `household_settings` too). `leaveHousehold` deletes exactly one `household_memberships` row and nothing else, and nothing cascades from a membership deletion. A per-user-per-household table like `notification_preferences` therefore needs an *explicit* cleanup path added to both resolvers when it lands, or it will leave orphaned per-user rows behind on every leave and stale rows after every delete. **Flag this as a blocking prerequisite check on the notification-preferences task**: before shipping that table, confirm (a) its FK to `households` declares `ON DELETE CASCADE`, and (b) `leaveHousehold` explicitly deletes the departing member's row in the same transaction.
- **A database-reviewer pass on this slice recommended a DB-level trigger making "no household loses its last `primary` membership" an enforced invariant, not just an application-code one — deliberately not added in this PR.** Today `deleteNonPrimaryMembership`'s `role <> 'primary'` predicate (see above) is the *only* thing preventing a primary-less household; a `BEFORE DELETE` trigger on `household_memberships` raising when the deleted row is a household's sole `primary` would turn that into a database-enforced invariant surviving any future code path that touches this table directly. Not added here because it requires a new migration (schema-level change) and this slice's own resolver-level check is already proven correct by a dedicated test (`deleteNonPrimaryMembership`'s `role <> 'primary'` predicate is empirically tested, not just documented) — expanding this PR's migration surface for defense-in-depth on an already-tested invariant was judged out of scope for this slice specifically. Recorded here, not silently dropped, as a candidate follow-up alongside the `households`/`household_memberships` RLS gaps above.

### W5 — first real `cdk deploy` to a live AWS account (six real bugs, none caught by any test)

- **Aurora PostgreSQL `16.4` (the version this codebase had hardcoded) is deprecated and unavailable for new clusters in `ap-south-1`.** `cdk deploy Parimaan-dev-Data` failed at `AWS::RDS::DBCluster` creation with `Cannot find version 16.4 for aurora-postgresql`. Confirmed the actually-available versions via `aws rds describe-db-engine-versions --engine aurora-postgresql --region ap-south-1`, cross-checked against the CDK library's own `AuroraPostgresEngineVersion` enum (older than AWS's live version list — `16.14` exists on AWS but has no CDK constant yet). **Resolved**: bumped to `AuroraPostgresEngineVersion.VER_16_13`, the latest 16.x both AWS and the installed CDK version actually support.
- **`serverlessV2AutoPauseDuration` is rejected outright unless `serverlessV2MinCapacity` is exactly `0`.** The stack had `serverlessV2MinCapacity: 0.5` alongside an explicit auto-pause duration (PRD §17.4 lever #2, cost discipline) — AWS's own API rejects that combination: `SecondsUntilAutoPause can only be specified when minimum capacity is 0`. The two settings' intents were actually in tension: a non-zero minimum keeps a warm instance permanently, which is the opposite of what auto-pause is for. **Resolved**: `serverlessV2MinCapacity: 0` — the fix that actually delivers the cost-discipline intent, not just satisfies the API.
- **pnpm's isolated `node_modules` layout broke the migration-runner Lambda's dependency bundling twice, at two different depths, each only surfacing on a real invocation.** `node-pg-migrate` is `externalModules` (esbuild can't statically bundle its `jiti`-based runtime file loading) and copied directly from this repo's own `node_modules` at bundle time. The existing approach (documented in this file's own W1 entry above) copied only `node-pg-migrate`'s own leaf package directory — but pnpm never nests a package's dependencies inside that package's own directory; they're **sibling** symlinks one level up, in the shared `.pnpm/<pkg>@<version>/node_modules/` snapshot directory. First failure: `Cannot find package 'glob'` (a `node-pg-migrate` dependency) at Lambda cold start. Fixed by copying the snapshot *parent* directory instead of the leaf — which fixed `glob`/`jiti`/`yargs`, then immediately exposed the identical bug one level deeper: `Cannot find module 'pg-types'` (a dependency of `pg`, itself a `node-pg-migrate` **peerDependency**, so not even reachable by walking `dependencies`). **Resolved properly, not patched again**: replaced the whole mechanism with a small recursive resolver (`resolveDependencyClosure` in `infra/stacks/data-stack.ts`) that walks the real transitive `dependencies` graph from two explicit roots (`node-pg-migrate` and `pg`, since the latter is a peer dependency the walk can't discover on its own) and copies every resolved package flat into the bundle's `node_modules/`. Verified directly against the actual synthesized bundle output (`ls` on `cdk.out/asset.*/node_modules/`) before the next deploy attempt, rather than re-deploying blind a third time. **Lesson: "copied the package and its nested deps" needs verifying against the actual bundle contents, not just re-reading the intent in a comment — the original W1 comment's claim ("including the package's own nested dependencies") was wrong twice over, both times for the same underlying reason.**
- **`require.resolve('<pkg>/package.json')` throws `ERR_PACKAGE_PATH_NOT_EXPORTED` for any package with a strict `exports` map that doesn't list that subpath** — hit while building the resolver above, on `lru-cache` (pulled in transitively via `glob`). Resolving the package's real entry point instead (`require.resolve(pkgName, {paths})`, which every requirable package must expose by definition) and locating the last `/node_modules/<pkgName>/` segment in that resolved path sidesteps the restriction entirely.
- **esbuild's ESM output silently breaks any bundled dependency that does a runtime (not static) `require()` of a Node builtin.** After the dependency-closure fix above, the migration runner failed differently: `Dynamic require of "node:https" is not supported`, from `@aws-sdk/client-secrets-manager`'s transitive `@smithy/node-http-handler`, which picks `http` vs `https` via a runtime `require()` esbuild can't statically resolve — under `OutputFormat.CJS` this is just `require`; under `OutputFormat.ESM` (needed for this Lambda's own `import.meta.url` usage — see the W1 entry above) esbuild replaces unresolvable `require` calls with a shim that throws unless a real `require` is in scope. **Resolved**: added `bundling.banner: "import { createRequire } from 'node:module'; const require = createRequire(import.meta.url);"` — esbuild's shim checks for exactly this before throwing. Verified the banner was actually present in the built `index.mjs` before redeploying.
- **CloudFormation's implicit dependency via `Fn::GetAtt AuroraCluster.Endpoint.Address` only waits on the `AWS::RDS::DBCluster` resource, not the separate `AWS::RDS::DBInstance` (the serverless-v2 writer) that resource depends on for the endpoint to actually resolve.** The migration-runner's CustomResource fired the moment the DBCluster resource alone reported complete, invoking the migration Lambda before the writer instance (and therefore the endpoint's DNS record) was ready: `getaddrinfo ENOTFOUND <cluster>.cluster-....rds.amazonaws.com`. **Resolved**: `migrationTrigger.node.addDependency(dbCluster)` — CDK's construct-level `addDependency` walks the *entire* construct subtree of its target and adds a CloudFormation `DependsOn` for every resource found there, which is what actually pulls the writer instance (a child construct of `dbCluster`, not visible as a separate top-level reference) into the wait. Verified the writer instance's logical id appeared in the synthesized `DependsOn` array before redeploying.
- **This specific AWS account's actual Lambda concurrency quota is 10 total** (`aws lambda get-account-settings` → `ConcurrentExecutions: 10`), not the commonly-assumed default of 1000 — evidently a fresh-account starting limit in this region. A `reservedConcurrentExecutions: 5` on each of the 9 DB-backed resolver Lambdas (added this session as a real Aurora-connection-exhaustion guard, since there is no RDS Proxy — Q1 locked decision) failed deployment outright: AWS rejects any reservation that would leave fewer than 10 unreserved. **Resolved for now, not abandoned**: removed the reservation (`api-stack.ts`'s `createDbResolverFunction` carries a comment with the exact re-add instructions and reasoning), since the account's own 10-execution ceiling already bounds simultaneous Aurora connections more tightly than the intended 45-connection cap would have — nothing is actually unprotected in the meantime. **Follow-up**: request a Lambda concurrency quota increase via Service Quotas before real traffic exists, then reinstate `reservedConcurrentExecutions`.

### Mobile build-time config — CfnOutputs and the manual transcription step

- **The Flutter app's build-time config values are now CDK `CfnOutput`s, and getting them into the app is a manual, per-environment step that nothing automates yet.** `AuthStack` exports `UserPoolId`, `MobileClientId` (the *public*, PKCE, `generateSecret: false` mobile client — never the confidential web client), `CognitoDomain` (the Hosted UI base URL), and `Region`; `ApiStack` exports `GraphQlUrl` (`this.api.graphqlUrl`). These five values are exactly what the mobile app needs before it can authenticate or issue a single GraphQL request, and they are the *only* outputs either stack declares — the Aurora endpoint, the `parimaan_app` secret ARN, and the Lambda security group are deliberately not exported (`api-stack.test.ts` asserts `Outputs` contains nothing but `GraphQlUrl`). Export names are env-scoped (`Parimaan-<env>-<Name>`) because CloudFormation export names are unique per account+region — unprefixed names would make the second environment's deploy fail against the first. **None of the five is a secret, and that is by design rather than an oversight**: the mobile client is a public client with no generated secret, so its id, the pool id, and the hosted-UI domain ship inside every mobile binary regardless (same category as the Google OAuth Client ID, already documented as non-sensitive on `AuthStackProps`), and the AppSync endpoint is Cognito-authorized on every request, so knowing the URL grants nothing.
- **Procedure (manual, run once per environment and again after any stack replacement):** `cd infra && pnpm cdk deploy Parimaan-<env>-Auth Parimaan-<env>-Api -c env=<env> -c googleClientId=<id>.apps.googleusercontent.com`, then read the five values off the `Outputs` block the CLI prints at the end of each stack and transcribe them into `mobile/lib/app/config/dev_config.dart`. **That file does not exist yet** — a later mobile slice creates it; it is recorded here now so the outputs have a named consumer rather than existing for no stated reason. Re-run the transcription whenever a Cognito user pool or app client is *replaced* rather than updated (Cognito's `Schema` is immutable post-creation, so an attribute change replaces the pool and changes the pool id) — a stale `dev_config.dart` fails at sign-in with an opaque Cognito error, not a config error. Do not commit real output values into this file; per the security constraint at the bottom of this runbook, they belong in `dev_config.dart` and the password manager, not in `docs/`.

### Mobile design tokens — hand-ported per Q12, with a stronger drift guard than the locked convention specified

- **`shared/design-tokens.json` is now the checked-in source of truth for the design system (colors, typography, spacing, radius, elevation, motion, iconography, accessibility minimums) — extracted verbatim from the actual design-system source file, not reconstructed from prose.** `E2E_MVP_PLAN.md`'s Q12 locks "hand-port, not codegen" and specifies a `docs/design-tokens-snapshot.json` drift-check convention: a snapshot created alongside the W1 hand-port, diffed by hand whenever a future session touches `theme.dart` or the design system. `docs/design-tokens-snapshot.json` now exists (a copy of `shared/design-tokens.json` at hand-port time) to satisfy that locked convention. **But the primary enforcement mechanism actually shipped is stronger than what Q12 specified**: `mobile/test/shared/ui/tokens_test.dart` parses `shared/design-tokens.json` at test time and asserts every Dart token constant (`AppColors`, `AppSpacing`, `AppRadius`, `AppElevation`, `AppMotion`, `AppTypography`, `AppSizing`) equals its JSON counterpart — a mechanical, CI-enforced check that fails the build on drift, not a "diff against a snapshot before proceeding" convention that depends on a future session remembering to look. Keep `docs/design-tokens-snapshot.json` updated alongside `shared/design-tokens.json` for doc compliance, but treat `tokens_test.dart` as the thing that actually prevents drift.
- **Two token names had no name in the source design-system file and were invented during the hand-port**: `AppColors.cardamomSoftForeground` (the source nests it as `cardamomSoft`'s paired foreground color with no top-level token name) and the secondary button's border width (the source specifies no border-thickness token at all; Flutter's default `BorderSide` width was used rather than a hardcoded literal). If a future design-system revision names these formally, reconcile `shared/design-tokens.json` and the two Dart constants together.
- **Font files were sourced from `github.com/google/fonts` at hand-port time, not the design-system source file itself (which contains no font binaries).** DM Sans, JetBrains Mono, and Noto Serif Devanagari are published there only as variable fonts; static weights were generated locally via `fontTools.varLib.instancer` (pinning `wght`, plus `opsz=14` for DM Sans and `wdth=100` for Noto) with no outline modifications — provenance recorded in `mobile/assets/licenses/OFL.txt`. Instrument Serif and Phosphor Regular are byte-verbatim upstream files. Phosphor Icons is MIT-licensed, not OFL — its attribution lives in a separate `mobile/assets/licenses/ICONS.txt` rather than being folded into the OFL file, since folding a different license into an OFL attribution file would misrepresent it.

### `Query.household` — correctly gated today, no rate limit for the polling load it's meant to carry

- **A security-reviewer pass on this resolver flagged a real, forward-looking gap: `Query.household` has no rate limiting, and it's explicitly intended to be the backing query for a future poll-based sync mechanism (`HouseholdSyncPolicy`, in lieu of the subscription deferred to W12).** As shipped — a single authorized read gated by `requireHouseholdMember`, same as `Query.me`/`User.households` — no rate limit is warranted, matching every other plain read in this codebase. The gap is specifically about what happens once a poll loop depends on it: N members each polling every few seconds turns this into sustained per-second load against Aurora (a VPC-attached Lambda doing `BEGIN`/`set_config`/multiple `SELECT`s/`COMMIT` per call) with no ceiling, a cost/availability concern distinct from the auth/injection surface this resolver was actually reviewed against (which is clean). **Not addressed in this PR** — `Query.household` ships as a correctly-gated read with nothing yet depending on it. **Flag this as a blocking prerequisite check before the `HouseholdSyncPolicy` polling mechanism ships**: add a lightweight per-caller rate limit at that point (e.g. `dailyActionLimiter.ts`'s pattern adapted to a short "requests per minute" window, or an AppSync-level per-caller throttle configured independently of Lambda-level limiting) rather than letting the mobile client depend on unrestricted polling before a limiter exists.

### W7 — two real bugs found by S12's live-deploy verification pass, plus new operational surface (Gemini key rotation)

- **A shared rate limiter's bare-constructor default message leaked one caller's copy onto three unrelated callers — invisible to 940 passing unit tests, caught only by actually hitting a real cap through the deployed Lambda.** `api/src/rateLimit/dailyActionLimiter.ts`'s `checkAndIncrementDailyAction` threw a bare `new RateLimitedError()` on every cap-exceeded call, which silently inherited `RateLimitedError`'s class-default constructor message (`"Too many join attempts. Try again tomorrow."`, written back when `joinHousehold` was its only caller). Once the limiter became shared across four daily caps, `parseFreeformRecipe`/`importRecipeFromUrl`/`rotateInviteCode` each surfaced that same join-specific copy on their own, unrelated rate limits — every existing test only asserted `errorType === 'RATE_LIMITED'`/`instanceof RateLimitedError`, never message content, so nothing caught it. Found live: S12's 20-call freeform-parse acceptance-measurement batch hit `parseFreeformRecipe`'s own 20/day cap on its 20th call and returned the wrong message. **Resolved** (PR #64): `RateLimitedError.message` is now a required constructor param (no default); `checkAndIncrementDailyAction` takes a required `rateLimitedMessage` argument threaded from each of the 4 call sites' own action-specific copy; added a message-content assertion at each call site's own rate-limit test, since `instanceof`-only checks are exactly what let this regress silently once. Lesson: a shared low-level utility inheriting a default written for its *first* caller is a trap the type system won't catch — a required parameter, not a sensible-sounding default, is what actually prevents a second caller from inheriting copy that was never written for it.
- **`fetchPage.ts`'s `DEFAULT_MAX_BYTES` cap (1MB) silently excluded one of S1's own originally-validated-usable sites once that site's real page grew past it.** S1's JSON-LD coverage spike (§13.5.12) measured `indianhealthyrecipes.com` as one of 14/20 usable-draft sites on 2026-08-28. S12's re-measurement through the actually-deployed `importRecipeFromUrl` mutation (not the spike script) found it now failing with the generic `UrlUnreadableError` — traced via a direct `fetchPage`/`validateSafeUrl` call against the real page to a `"Response exceeded the size cap."` abort, not an SSRF-gate rejection or a parse failure: the live page is ~1.13MB, up from whatever it was at S1's original capture date. **Resolved**: raised `DEFAULT_MAX_BYTES` to 5MB (`api/src/net/fetchPage.ts`) — the cap's actual job (bounding a malicious server streaming unbounded data into this Lambda's 512MB memory budget) is already mostly done by the existing 8s total-timeout, and AWS doesn't bill inbound transfer, so neither the security nor the cost rationale the original 1MB was tuned against moves meaningfully at 5MB. Re-verified live post-deploy: 14/20 (70%), matching S1's original number exactly, with `indianhealthyrecipes.com` recovered. Lesson: a defensive byte/size cap tuned against a real page's size at spike time is not a one-time decision — real third-party pages grow, and a cap with no periodic re-check silently converts "page too big right now" into "site permanently broken" with no signal anywhere that it happened, since both look identical (`UrlUnreadableError`) to the caller by design (§13.2.10's "never distinguishes why" contract).
- **New operational surface: the Gemini API key lives in Secrets Manager (`parimaan/gemini-api-key`, a `{"apiKey": "..."}` JSON secret, referenced by `GEMINI_API_KEY_SECRET_ARN`) and is fetched once per Lambda execution environment, not once per invocation.** `api/src/ai/geminiClient.ts`'s `apiKeyPromise` is a module-scope memoized value — mirrors `db/pool.ts`'s connection-pool memoization pattern exactly — so a warm `ParseFreeformRecipeFn` container keeps using whatever key it fetched at its own cold start until that container is naturally recycled by AWS, which can be minutes to hours later. **Rotation procedure**: (1) generate a new key in Google AI Studio; (2) update the `parimaan/gemini-api-key` secret's `apiKey` value via `aws secretsmanager put-secret-value` (or the console) — this alone does **not** immediately affect already-warm containers; (3) if the old key must stop working immediately (compromise, not routine rotation), force every warm container to cycle by publishing a new Lambda version / updating the function's own configuration (e.g. `aws lambda update-function-configuration` with a no-op env var touch) rather than waiting for natural recycling; (4) confirm via one real `parseFreeformRecipe` invoke (same direct-Lambda-invoke method as S12's own verification pass) that a fresh call succeeds against the rotated key. For routine (non-compromise) rotation, waiting out natural container recycling is fine and simpler — this distinction (routine vs. compromise) is the one thing worth deciding explicitly before rotating, not during.

### W10 — live concurrency verification against real dev Aurora (repeatable procedure)

Recorded because this is now the second week running (W9 S7, W10 S7) that a cap-enforcement or lock-ordering change has needed exactly this proof and it was re-derived from scratch both times. It is the live counterpart to the Testcontainers concurrency tests, not a replacement for them: Testcontainers proves the SQL is right, this proves the *deployed* Lambdas, the *deployed* Aurora, and real network latency between them agree with it.

**Why direct Lambda invoke and not psql.** Aurora sits in an isolated VPC subnet with no route from a developer machine, and the RDS Data API is **disabled** on the cluster (`aws rds describe-db-clusters --query "DBClusters[].HttpEndpointEnabled"` → `false`; there is no `enableDataApi` in `infra/stacks/data-stack.ts`). Direct Lambda invoke against the deployed resolvers is therefore the only path in, not merely the convenient one. Do **not** enable the Data API or add an admin/arbitrary-SQL resolver just to run a verification query — that is a real security-surface change and belongs in a reviewed PR of its own, not inside a verification pass.

**Prerequisites**

- `AWS_PROFILE=parimaan-dev`, region `ap-south-1`. Confirm with `aws sts get-caller-identity` before anything else.
- Physical Lambda names from `aws lambda list-functions --query "Functions[].FunctionName"` — they carry CloudFormation hashes (`Parimaan-dev-Api-<Resolver>Fn<hash>-<suffix>`) and **change on stack replacement**, so look them up fresh each pass rather than reusing a previous week's list.
- Founder authorization for the pass. This writes to the real dev database.

**Event shape.** Every resolver Lambda expects an AppSync-direct-resolver-shaped event with a synthetic Cognito identity — a fresh UUID per throwaway user, so the pass can never collide with or read a real one:

```json
{
  "arguments": { "...": "the operation's own GraphQL arguments" },
  "identity": {
    "sub": "<uuid>",
    "username": "<uuid>",
    "claims": { "email": "<uuid>@example.test" }
  }
}
```

Invoke with `aws lambda invoke --function-name <name> --payload fileb://<payload>.json <out>.json`. Prefer `fileb://` over an inline `--payload` string: it avoids shell quoting entirely and makes the payload reviewable after the fact. A thrown resolver error surfaces as `FunctionError` in the invoke result with the client-safe `{errorType, errorMessage}` in the output file — that is the same message a real GraphQL client would see, so it is a legitimate assertion target.

**Procedure**

1. **Create throwaway state through the real resolvers only** — `createHousehold` → `updateHouseholdSettings` → `createRecipe` (×N) → `createMenu`. Never touch a pre-existing household, user, recipe, or menu; a fresh synthetic `sub` guarantees membership in nothing else.
2. **Configure the narrowest cap that still exercises the rule.** For a cap race, one meal enabled with one role at cap 1 (`mealsEnabled: ["lunch"]`, `mealStructure: {"lunch": {"carb": 1}}`) makes the assertion a single integer and removes every confounder.
3. **Fire the racing invokes genuinely in parallel**, not sequentially — two independent processes, e.g. `Promise.all` over two `aws lambda invoke` child processes in a throwaway Node script, or two backgrounded shell invokes. Sequential calls prove nothing about locking. Keep the script in a scratch directory; spike tooling is not committed.
4. **Assert on final state, not on the responses alone.** Read the result back with `Query.menu` and count rows per `(dayOfWeek, mealSlot, slotRole)`. The count is the real assertion; the responses only tell you *how* the loser lost.
5. **Distinguish the three possible losses explicitly**, because they are not equivalent: a rejection carrying the domain message (`"This meal slot is full."` — `addMenuItem`'s contract), a silent skip reported honestly as a lower `filledCount` (`autoFillWeek`'s best-effort-partial contract), and a **deadlock** (never acceptable — it means the two lock namespaces are being acquired in inconsistent order). Grep both responses for a deadlock error specifically; do not infer its absence from a passing row count.
6. **Run the cross-path race too, not just the same-path one.** Two `autoFillWeek` commits exercise one lock ordering; `autoFillWeek` racing `addMenuItem` exercises the interaction between two different code paths, which is where the W10 §16.2.6 lock-ordering change actually created risk.
7. **Delete everything, then prove it.** `deleteHousehold(householdId, confirmationName)` with the exact household name, then a follow-up `Query.household` on the id. Expect the no-existence-oracle denial (`"You are not a member of this household."`) rather than a not-found — that message is the same whether the household was deleted or never existed, by design, so treat it as the expected result and not as an error in the cleanup.

**Recording the result.** Write the actual counts and the actual response messages into that week's own result subsection in `E2E_MVP_PLAN.md` (§15.9, §16.9) — never "no deadlock observed" without the row counts and the two responses that back it.

## 3. Two-Device Verification Procedure

Written for the W5 S9 DoD gate (E2E_MVP_PLAN.md §11.3 S9: "add/edit/delete on A appears on B, **timed**, target <5s") and re-run unchanged at W8, W11, and W12 against whatever entity that week's subscription covers (household settings, shopping list, pantry-via-menu). Requires a human running two real physical devices — this cannot be automated or delegated.

### Prerequisites

- Two physical devices (iOS or Android, any mix), each on a real network connection — **not** the same Wi-Fi's loopback or a simulator/emulator pair, since the point is to exercise the real AppSync WebSocket path end to end.
- Two separate Google accounts, neither of which has signed into this app before (a clean first-run avoids a stale cached session muddying the timing).
- The dev backend deployed and reachable (`docs/RUNBOOK.md` §2's AWS deploy notes if it isn't already).
- A stopwatch, or the "time elapsed" indicator on whichever screen-recording tool is used to capture both devices at once — the target is measured, not eyeballed.

### Procedure

1. **Device A:** sign in with Google account 1, create a new household (any name), reach the Pantry tab.
2. **Device B:** sign in with Google account 2, join the household using the invite code from Device A, reach the Pantry tab.
3. Confirm both devices show the same (empty) pantry list before starting the timed steps — this is the baseline, not part of the measurement.
4. **Add, timed:** on Device A, add one pantry item (any name/quantity/unit). Start the stopwatch the moment the add confirms on A; stop it the moment the new row appears on B without B's user taking any action (no manual pull-to-refresh, no re-entering the screen). Record the elapsed time.
5. **Edit, timed:** on Device B, edit that same item (change quantity or name). Start the stopwatch on confirm; stop when the change appears on A. Record.
6. **Delete, timed:** on Device A, delete the item. Start the stopwatch on confirm; stop when the row disappears from B. Record.
7. Repeat steps 4–6 once more (a second sample) — a single run can be misleadingly fast or slow depending on connection jitter; two runs is the minimum to say the number is representative, not lucky.

### W8 additions (D6): burst and forced-reconnect samples

E2E_MVP_PLAN.md §14.2.5/D6 defines W8's "2-device sync <5s **under load**" as event rate and recovery, not client count (R3's 5-concurrent-client soak stays W11, named out of scope so an unchecked R3 box is never misread as a W8 miss). Two samples, additive to the six above, not a replacement for them:

8. **Burst, timed:** on Device A, perform ~20 rapid sequential mutations (any mix of add/edit/delete against the entity this week's subscription covers). Start the stopwatch on the *first* mutation's confirm; stop it the moment the *last* one's effect appears correctly on Device B. Record the elapsed time and confirm B's final state matches A's exactly (no dropped, duplicated, or out-of-order mutation) — a burst that arrives fast but wrong is a worse finding than one that arrives slow but correct.
9. **Forced-reconnect, timed:** with both devices connected and subscribed, drop Device B's network (airplane mode, or disconnect Wi-Fi) for at least 10s, then restore it. Start the stopwatch the moment the network is restored; stop it when Device B shows a correct, up-to-date list without the user taking any action beyond what backgrounding/foregrounding or the reconnect ladder already does automatically. Record the elapsed time and which mechanism actually closed the gap (a live reconnect + resubscribe, or the route-entry/foreground refetch catching up behind it).

**W8 S12 status: defined, not yet run.** This procedure requires a human running two real physical devices with two clean Google accounts (see Prerequisites above) — explicitly not something a coding session can automate or delegate, and not satisfied by the D8 simulator-pair method used elsewhere in W8 (that method is reserved for cases with no hardware access at all; this specific gate's own prerequisites rule it out by name). S12's real-AWS verification pass (E2E_MVP_PLAN.md §14.5.10) covered every backend slice via direct Lambda invoke instead, which is a different kind of proof and does not substitute for a timed device-to-device sample. Stays open until a human runs steps 1–9 against the (now current) dev deploy and records real numbers here.

### Recording the result

Write the actual numbers — never "felt fast" or "seemed instant" — into `E2E_MVP_PLAN.md` §4's row for the week being verified (W5/W8/W11/W12), plus a one-line pass/fail against the <5s target. If any sample exceeds 5s, note which of add/edit/delete and don't round it away; a slow outlier is exactly the kind of thing this gate exists to catch before it reaches a real household.

### If it fails

- **Consistently >5s on every sample:** check the AppSync CloudWatch logs for the subscription resolver's invocation latency first — a cold VPC Lambda (the `onPantryChanged` resolver is VPC-attached, same Aurora-auto-pause cold-start risk as every other DB-backed resolver) can add several seconds on the *first* call after a period of inactivity. Re-run once more before concluding the sync path itself is slow, not just cold.
- **Never arrives at all (not just slow):** confirm Device B's WebSocket actually connected — the mobile app has no visible connection indicator yet (W5 S8 shipped subscribe/unsubscribe only, no reconnect UI), so a silently-failed `connection_init` looks identical to "still loading." Check `AppSyncSubscriptionClient`'s behavior isn't the first thing to suspect here if this is W8+ (reconnect backoff exists by then); for W5 specifically, a connection that failed to establish at all simply never retries — background/foreground the app to force a fresh `PantryController.build()` and a new subscribe attempt.
- **Works on Wi-Fi, fails on cellular:** expected and out of scope for this gate — E2E_MVP_PLAN.md §11.3 S8 already documents that a good-wifi two-device demo passing "while the mechanism is still fragile on a subway" is a known, accepted gap until W8's reconnect backoff and W11's 5-concurrent-client load spike land.
